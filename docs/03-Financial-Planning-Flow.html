Financial Planning Module

SyncUp — AI Operations Manager for Student Organizations

MEMBER C   Module 3 of 3  ·  api/app/features/finance/  ·  Monolith: FastAPI · React · Supabase Postgres · Microsoft Foundry

Architecture note. SyncUp is a single FastAPI process. Your module is a Python package that scheduling imports and calls directly, sharing the same AsyncSession and the same transaction. There is no HTTP call and no eventual consistency between modules — which matters more here than anywhere else, because money must never be committed against an event that failed to save.

1. Module Scope

Financial planning drafts an itemized budget from an event description, checks it against the org's remaining semester allocation, tracks actual expenses against estimates, and warns before the org overspends. It closes the loop: scheduling picks the time, resources decide what is needed, finance decides whether the org can afford it.

Money rule: all amounts are NUMERIC(12,2) in PostgreSQL and Decimal in Python — never float, and never a JSON float on the wire (serialize as strings). The LLM proposes numbers; Python performs every arithmetic operation. A budget whose column does not add up is the single most damaging thing a judge can notice.

5. Headroom Model

Three distinct numbers — conflating them is the classic bug in budget software.

flowchart LR
  A["allocated
semester budget"] --> D["remaining"]
  B["committed
approved, not yet spent"] --> D
  C["actual
logged expenses"] --> D
  D --> E{"remaining minus proposed"}
  E -- "zero or above" --> F["verdict OK"]
  E -- "down to -10% of allocation" --> G["verdict TIGHT
warn, still allow"]
  E -- "worse than -10%" --> H["verdict OVER
block, require cuts"]

# app/features/finance/headroom.py — pure, no I/O
from decimal import Decimal

def check(allocated: Decimal, committed: Decimal,
          actual: Decimal, proposed: Decimal) -> Headroom:
    remaining = allocated - committed - actual
    after     = remaining - proposed
    if after >= 0:
        verdict = "OK"
    elif after >= -(allocated * Decimal("0.10")):
        verdict = "TIGHT"
    else:
        verdict = "OVER"
    return Headroom(remaining=remaining, after=after, verdict=verdict)

# committed = SUM(estimated_total) WHERE status='approved'
#             AND event.status IN ('draft','confirmed')
# actual    = SUM(expenses.amount) WHERE status IN ('approved','reimbursed')
# Once an event completes, committed is replaced by actual — no double count.

Never call db.commit() inside draft_for_event(). Scheduling owns the transaction. If you commit early and a later step fails, you have a budget committed against an event that does not exist — the exact class of bug the monolith exists to prevent. Your functions receive a session and use it; they never manage its lifecycle.

Import direction: scheduling imports finance. Finance must never import scheduling — receive the Event as an argument. Shared types belong in app/core/types.py.
