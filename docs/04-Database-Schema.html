Database Schema

SyncUp — one PostgreSQL database for one monolith application

Supabase Postgres 16 · SQLAlchemy 2.0 async · single Alembic chain  ·  SHARED SCHEDULING · A RESOURCES · B FINANCE · C

Monolith consequences for the database. One application process means: one database, one public schema, one SQLAlchemy MetaData, one linear Alembic migration chain, and one connection pool. Foreign keys cross module boundaries freely, and a single transaction can span all three modules' tables — which is exactly what the confirm flow relies on. None of this would be available if each feature were its own service.

1. Ownership Map

Every table has exactly one writer module; the others read. This is a code-review convention, not a database permission — but it is the single rule that lets three people share one schema for 24 hours without collisions.

OwnerModel fileWrites
SHAREDapp/models/org.pyorganizations, members, venues, ai_interactions
MEMBER Aapp/models/scheduling.pybusy_blocks, scheduling_requests, slot_proposals, events, event_attendees
MEMBER Bapp/models/resources.pyresources, resource_reservations, packing_list_items
MEMBER Capp/models/finance.pybudgets, event_budgets, budget_line_items, expenses

One Alembic chain, three files

Because there is one database, there is one linear revision history. Migrations are strictly sequential — B cannot generate their migration until A's is merged, and C cannot until B's is.

alembic/versions/
├── 0001_core.py        # A — hour 0-2. down_revision = None
├── 0002_resources.py   # B — branches from 0001
└── 0003_finance.py     # C — branches from 0002
The most likely database failure in your 24 hours: two members run alembic revision --autogenerate from the same parent, producing two heads. Alembic then refuses to upgrade with "Multiple head revisions are present". Avoid it by sequencing: A merges, then B generates; B merges, then C generates. If it happens anyway, edit one file's down_revision to point at the other rather than reaching for alembic merge under time pressure.

All three model files must be imported in app/models/__init__.py before Base.metadata is read, or autogenerate will silently propose dropping the tables it cannot see.

3. Write Paths Inside One Transaction

The confirm flow writes to all three modules' tables in a single transaction opened by scheduling. This diagram shows what the database sees.

flowchart TB
  BEGIN(["BEGIN — opened by scheduling/service.py"]) --> E1["INSERT events"]
  E1 --> E2["INSERT event_attendees"]
  E2 --> E3["UPDATE slot_proposals SET selected"]
  E3 --> R1["resources.plan_for_event: same session"]
  R1 --> R2["INSERT packing_list_items"]
  R2 --> R3["INSERT resource_reservations status=held"]
  R3 --> F1["finance.draft_for_event: same session"]
  F1 --> F2["INSERT event_budgets status=draft"]
  F2 --> F3["INSERT budget_line_items"]
  F3 --> COMMIT(["COMMIT — all or nothing"])
  R3 -.->|"exclusion constraint violation"| RB(["ROLLBACK
event never existed"])
  F2 -.->|"any exception"| RB
This is the schema-level argument for the monolith. If a resource conflict is detected by the exclusion constraint at step R3, the event insert at step E1 rolls back with it. There is no compensating transaction, no orphaned event, no cleanup job. Across three services this would be a distributed-saga problem; in one process it is async with db.begin():.

4. Session & Pool Configuration

One process, one pool, one session per request — plus one long-lived session pattern for the Discord bot.

# app/db.py
engine = create_async_engine(
    settings.database_url,        # Supabase SESSION POOLER host, +asyncpg
    pool_size=5,                  # Render free = 1 instance; keep small
    max_overflow=5,
    pool_pre_ping=True,           # survives Supabase/Render idle disconnects
    pool_recycle=1800,
)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

# FastAPI request scope
async def get_db():
    async with SessionLocal() as session:
        yield session

# Discord command scope — bot handlers are NOT in a request,
# so they open their own session explicitly.
async def with_session(fn, *args, **kwargs):
    async with SessionLocal() as session:
        return await fn(session, *args, **kwargs)
Two Supabase gotchas that will cost you an hour each.
1. Use the Shared Pooler (Supavisor) connection string, not the direct one. On the free plan the direct host is IPv6-only and Render has no IPv6 egress — you will get an opaque connection timeout that looks like a firewall issue.
2. Supabase gives you postgresql://; SQLAlchemy async needs postgresql+asyncpg://, and asyncpg rejects the ?sslmode= parameter that libpq accepts. Rewrite the prefix and strip that query param in config.py so nobody has to remember.

5. Key Design Decisions

DecisionRationale
Single public schema, no per-module schemasOne app, one owner. Per-module schemas add qualified names and Alembic friction for zero benefit in a monolith
UUID PKs (gen_random_uuid())Three developers seeding independently; no sequence collisions when merging fixtures
Real foreign keys across module boundariesAvailable precisely because it is one database — referential integrity for free, no orphan-cleanup jobs
All timestamps TIMESTAMPTZ, stored UTCTimezone bugs are the classic scheduling demo killer. Convert to org-local only in the UI
Money as NUMERIC(12,2)Float arithmetic on currency produces totals that visibly do not add up
JSONB for parsed_constraints and conflictsLLM output shape changes hourly during a hackathon; JSONB avoids re-migrating
btree_gist exclusion constraintDouble-booking becomes impossible at the data layer regardless of application logic
GiST indexes on tstzrangeOverlap queries are the hottest path in both scheduling and resources
TEXT + CHECK instead of PG ENUMAdding an enum value mid-hackathon needs a migration and can block; a CHECK is a one-line change
Soft status columns, no hard deletesCancelled events and released holds stay visible for audit and variance views
ai_interactions log tableJudges reliably ask "how do you know the AI is right?" — logged prompts, tool calls, and latency answer it

6. Indexes That Matter

-- Overlap queries: scheduling availability + resource conflicts
CREATE INDEX idx_busy_blocks_range ON busy_blocks
  USING gist (member_id, tstzrange(start_utc, end_utc));

CREATE INDEX idx_reservations_range ON resource_reservations
  USING gist (resource_id, tstzrange(start_utc, end_utc));

CREATE INDEX idx_events_org_time ON events (org_id, start_utc)
  WHERE status IN ('draft', 'confirmed');

-- Hot lookups
CREATE INDEX idx_members_org       ON members (org_id);
CREATE INDEX idx_members_discord   ON members (discord_user_id);
CREATE INDEX idx_line_items_budget ON budget_line_items (event_budget_id);
CREATE INDEX idx_expenses_budget   ON expenses (event_budget_id);

-- Historical price priors for the budget builder
CREATE INDEX idx_line_items_category ON budget_line_items (category, created_at DESC);

-- Expiring-hold sweep, runs every 5 minutes
CREATE INDEX idx_reservations_expiry ON resource_reservations (expires_at)
  WHERE status = 'held';

9. Applying the Schema

# Local, against the dev Supabase project
cd api
alembic upgrade head
python scripts/seed.py

# Production — runs automatically in the Render build command
pip install -e . && alembic upgrade head

# Or apply the raw DDL directly, e.g. in the Supabase SQL editor
psql "$DATABASE_URL" -f schema.sql

The complete schema.sql ships alongside this document. Extensions first — pgcrypto and btree_gist must be enabled in the Supabase SQL editor before the first migration runs.
