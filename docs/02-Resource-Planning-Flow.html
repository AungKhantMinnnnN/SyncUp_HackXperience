Architecture note. SyncUp is a single FastAPI process. Your module is a Python package that scheduling imports and calls directly, sharing the same AsyncSession and the same transaction. There is no HTTP call, no queue, and no eventual consistency between modules.

1. Module Scope

Resource planning answers “what do we need, do we have it, and is anyone else using it?” It maintains the org's inventory of equipment and venues, uses the LLM to infer a packing list from an event description, and places time-bounded reservations — applying the same conflict-detection rigour to objects that scheduling applies to people.

Core idea to pitch: a projector booked 7–9pm Thursday is structurally identical to a person being busy 7–9pm Thursday. Resource conflicts run through the same interval-overlap primitive as calendar conflicts. One abstraction, two modules.

4. Conflict Detection Logic

The whole module rests on one query. Get it right and everything else is CRUD.

flowchart TD
  A["Request: resource R, quantity Q, window S to E"] --> B["SELECT quantity_total FROM resources WHERE id=R"]
  B --> C["SELECT COALESCE SUM quantity FROM resource_reservations
WHERE resource_id=R
AND status IN held, confirmed
AND tstzrange overlaps window"]
  C --> D["available = quantity_total - reserved"]
  D --> E{"available >= Q?"}
  E -- yes --> F["Create reservation status=held
expires_at = now + 30 min"]
  E -- "partial availability" --> G["Reserve available portion
shortfall = Q minus available"]
  E -- "none available" --> H["Hard conflict"]
  G --> I["LLM suggests alternatives"]
  H --> I
  I --> J["Return conflict object
with blocking event name"]
  F --> K["Return OK"]
  K --> L{"Approved within TTL?"}
  L -- yes --> M["status = confirmed"]
  L -- "TTL expires" --> N["expire_holds job: status = released"]

Preventing the double-book race in PostgreSQL

Two organizers approving at the same moment must not both get the projector. Push it into the database rather than the application — a strong technical detail for judging, and one that keeps working no matter what the code does.

-- In migration 0002_resources
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- Exclusive items: any overlap is impossible, enforced by the schema
ALTER TABLE resource_reservations
  ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(start_utc, end_utc) WITH &&
  ) WHERE (exclusive = true AND status IN ('held','confirmed','checked_out'));

Monolith rule: never call db.begin() or db.commit() inside your service functions. Scheduling opens the transaction and commits it. If you commit halfway through, a later failure in finance can no longer roll back your reservations — and the org ends up with equipment held for an event that was never created. Your functions take an AsyncSession and use it; they never manage its lifecycle.

6. Packing List Inference

The LLM's job is narrow and safe: map an event description onto the org's existing catalogue, and flag anything needed that the org does not own.

flowchart LR
  A["Event title, description
expected_attendance"] --> B["Prompt with org catalogue
injected as structured context"]
  B --> C["Foundry LLM
JSON schema output"]
  C --> D{"Name matches catalogue?"}
  D -- yes --> E["Link resource_id server-side
quantity scaled by attendance"]
  D -- no --> F["Unowned item"]
  F --> G["Returned to scheduling, passed to
finance as equipment_rental line"]
  E --> H["Availability check"]
  H --> I["packing_list_items rows"]
  G --> I
Guardrail: constrain the model to a JSON schema and validate with Pydantic. Match resource IDs server-side by name — never trust IDs the model emits. Unmatched names fall into the unowned path rather than raising. The pattern generalizes: the model proposes in an open vocabulary, the system resolves against a closed one.
